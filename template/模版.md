# 模版

> 关于项目、文件、工程的一些统一的模版和prompt



## 以"#"为注释的文件

  ### yaml

  1. 适用：.yaml / .yml
  2. 特点：配置项多、层级结构明显、行尾解释重要

  3. Prompt 模板

    ~~~ prompt
      你是一个严谨的工程配置维护者，请为我提供的 YAML 文件补充高质量注释，要求如下：
    
      【注释风格】
      - 使用 # 作为注释符号
      - 注释语言为中文
      - 注释解释“该配置的作用和用途”，不解释 YAML 语法
      - 避免空洞描述，如“这是一个配置项”
      - 要简练挑重点难点完成注释
      - 要求简洁，简洁，简洁，重要的事情说三遍


​    
​      【分区规则（必须遵守）】
​      - 逻辑模块之间使用如下分区格式：（上下都是空行）
​    
        # -------------------------------
        #  模块名称 / 功能说明
        # -------------------------------
    
      - 分区标题要概括“这一组配置在干什么”
    
      【单条配置注释规则】
      - 简单 / 关键配置：使用【行尾注释】
    
        key: value  # 说明该配置的实际用途
    
      - 复杂 / 易混淆 / 有约束的配置：
        - 在该行前增加注释说明
        - 必要时说明使用场景或注意事项
    
      【其他要求】
      - 保持原有缩进和结构不变
      - 不新增无意义的注释
      - 输出完整、已注释好的 YAML 文件
    ~~~ 

  ### shell 脚本

  1. 适用：.sh
  2. 特点：执行流程清晰、每一步有“意图”

  3. Prompt 模板

      ~~~prompt
        你是一个熟悉 Linux 脚本和工程自动化的工程师，请为我提供的 Shell 脚本补充清晰、可维护的注释，要求如下：
      
        【注释风格】
        - 使用 # 作为注释符号
        - 注释语言为中文
        - 注释重点是“这一步在做什么”“为什么要这样做”
        - 不解释显而易见的 shell 语法（如 echo、cd 等）
        - 要简练挑重点难点完成注释
        - 要求简洁，简洁，简洁，重要的事情说三遍
        
        【分区规则（必须遵守）】
        - 脚本逻辑块之间使用如下格式分区：（上下都是空行）
      
          # ----------------------------------------------------------------------------
          #  功能模块说明
          # ----------------------------------------------------------------------------
      
        - 分区用于表示阶段或功能（如：环境准备 / 构建 / 清理）
      
        【单步注释规则】
        - 每一个关键命令或命令组：
          - 在其上一行添加注释说明用途
        - 条件判断、循环、关键变量定义：
          - 必须说明其作用或影响范围
      
        【其他要求】
        - 保持脚本可直接执行
        - 不改变原有命令顺序和行为
        - 输出完整、已注释好的 .sh 文件
      ~~~

  ### CMakeList.txt

  1. 适用：CMakeLists.txt
  2. 特点：标准化强、步骤固定、适合“大分区 + 单步解释”
  3. Prompt 模板

    ~~~prompt
      你是一个熟悉 CMake 和工程构建流程的工程师，请为我提供的 CMakeLists.txt 文件补充规范、工程化的注释，要求如下：
    
      【注释风格】
      - 使用 # 作为注释符号
      - 注释语言为中文
      - 注释解释“这一段配置在构建流程中的作用”
      - 不解释 CMake 语法细节
      - 要简练挑重点难点注释,不用加什么锁定最低版本
      - 要求简洁，简洁，简洁，重要的事情说三遍
      
      【分区规则（必须遵守）】
      - 使用如下格式进行逻辑分区：（上下都是空行）
    
        # ----------------------------------------------------------------------------
        #  模块名称（如：查找依赖 / 构建目标 / 安装规则）
        # ----------------------------------------------------------------------------
    
      - 每个主要阶段必须有清晰分区
    
      【单步注释规则】
      - 对于关键指令（如 project / find_package / add_library 等）：
        - 在其上一行添加简明说明
      - 对于容易混淆的变量或路径：
        - 在同一行或上一行说明用途或约束
    
      【其他要求】
      - 不改变任何构建行为
      - 保留原始顺序
      - 输出完整、已注释好的 CMakeLists.txt
    ~~~
  4. 范例

    ~~~CMakeLists.txt
      # 指定 CMake 最低版本要求
      cmake_minimum_required(VERSION 3.8)
    
      # 定义当前项目名称，必须与 package.xml 保持一致
      project(usb_cdc)
    
      # 设置 C++ 标准
      set(CMAKE_CXX_STANDARD 17)
      set(CMAKE_CXX_STANDARD_REQUIRED ON)
    
      # 生成 compile_commands.json，供 clangd 使用
      set(CMAKE_EXPORT_COMPILE_COMMANDS ON)
    
      set(MY_ROBOT_INTERFACE "${CMAKE_CURRENT_SOURCE_DIR}/../../robots/engineer/engineer_interface")
    
      # 添加 GCC/Clang 编译器警告
      if(CMAKE_COMPILER_IS_GNUCXX OR CMAKE_CXX_COMPILER_ID MATCHES "Clang")
        add_compile_options(-Wall -Wextra -Wpedantic)
      endif()
    
      # ----------------------------------------------------------------------------
      #  查找依赖
      # ----------------------------------------------------------------------------
    
      # ROS2 自动依赖工具
      find_package(rclcpp REQUIRED)
      find_package(rclcpp_components REQUIRED)
      find_package(std_msgs REQUIRED)
      find_package(std_srvs REQUIRED)
      find_package(tf2_ros REQUIRED)
      find_package(tf2_geometry_msgs REQUIRED)
      find_package(sensor_msgs REQUIRED)
      find_package(engineer_interfaces REQUIRED)
    
      # pkg-config 工具（用于查找系统库）
      find_package(PkgConfig REQUIRED)
    
      # 查找 libusb-1.0 库
      pkg_check_modules(LIBUSB REQUIRED libusb-1.0)
    
      # ----------------------------------------------------------------------------
      #  构建节点可执行文件
      # ----------------------------------------------------------------------------
    
      add_library(${PROJECT_NAME} SHARED 
        src/usb_cdc_node.cpp
        src/usb_cdc_driver.cpp
      )
    
      # 添加头文件目录
      target_include_directories(${PROJECT_NAME} PUBLIC
        ${LIBUSB_INCLUDE_DIRS}                                  # libusb 头文件
        $<BUILD_INTERFACE:${MY_ROBOT_INTERFACE}>
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>  # 本项目 include
      )
    
      # 添加 libusb 的库目录搜索路径
      target_link_directories(${PROJECT_NAME} PUBLIC
        ${LIBUSB_LIBRARY_DIRS}
      )
    
      # 连接系统库 libusb-1.0
      target_link_libraries(${PROJECT_NAME}
        ${LIBUSB_LIBRARIES}
      )
    
      # 连接 ROS2 依赖
      ament_target_dependencies(${PROJECT_NAME}
        rclcpp
        rclcpp_components
        std_msgs
        std_srvs
        tf2_ros
        sensor_msgs
        engineer_interfaces
      )
    
      rclcpp_components_register_node(${PROJECT_NAME}
        PLUGIN usb_cdc::UsbCdcNode
        EXECUTABLE usb_cdc_node
      )
    
      install(TARGETS ${PROJECT_NAME} 
        ARCHIVE DESTINATION lib
        LIBRARY DESTINATION lib
        RUNTIME DESTINATION bin
      )
    
      install(DIRECTORY  launch/
          DESTINATION share/${PROJECT_NAME}/
      )


      # 生成 ROS2 包信息
      ament_package()
    ~~~

### launch.py

  1. prompt

    ~~~prompt
    
      你是一个工程化 ROS2 Launch Python 文件维护者。请对我提供的 .py 文件补充统一风格的 # 注释，要求如下（必须严格遵守）：
    
      【总体原则】
      - 只补充注释，不改变代码行为、调用顺序、变量名、缩进结构
      - 注释语言为中文（可含少量英文术语：TF / joint_state / MoveIt / controller 等）
      - 注释重点解释：参数含义、节点作用、链路关系（谁订阅谁/发布谁/依赖谁）
      - 不解释显而易见的 Python 语法
      - 要求简洁，简洁，简洁，重要的事情说三遍
    
      【1) 顶层结构必须分为 3 大块（固定顺序）】
      (1) 导入库文件
      (2) 可复用函数
      (3) 启动函数
    
      每个大块必须使用如下分区格式：（上下都是空行）
    
      # ----------------------------------------------------------------------------
      #  <分区标题>
      # ----------------------------------------------------------------------------
    
      例如：
      # ----------------------------------------------------------------------------
      #  导入库文件
      # ----------------------------------------------------------------------------
    
      【3) 可复用函数区】
      - 必须使用：（上下都是空行）
        # ----------------------------------------------------------------------------
        #  可复用函数
        # ----------------------------------------------------------------------------
      - 每个函数只在必要处补充简短注释：
        - 说明用途（读文件/读 yaml/处理 xacro）
        - 说明返回值/失败策略（例如异常返回空字符串）
      - 不写长篇“函数逐行翻译”
    
      【4) 启动函数区（最重要）】（上下都是空行）
      - 在 generate_launch_description() 前必须添加：
    
      # ----------------------------------------------------------------------------
      #  启动函数
      # ----------------------------------------------------------------------------
    
      - 在 generate_launch_description() 内部，必须按“配置来源 → 路径 → 参数字典 → 节点/动作定义 → 返回 LaunchDescription”的逻辑分区
      - 分区使用短分区格式：（上下都是空行）
    
      # -------------------------------
      #  <小分区标题>
      # -------------------------------
    
      常见小分区标题示例（按实际内容选用）：
      - 自定义路径
      - 普通参数列表
      - 重要参数说明
      - 节点定义
      - 定时/事件动作
      - LaunchDescription 组装
    
      【6) 关键节点/启动项说明（必须支持）】（上下都是空行）
      每个关键 Node / TimerAction / IncludeLaunchDescription 等启动项，在定义前必须写：
    
      # -------------------------------------------------------------------------------
      #  <节点/动作名称> 节点（或动作）：说明
      # -------------------------------------------------------------------------------
      
      示例风格（需按实际内容改写，不要照抄）：
      # -------------------------------------------------------------------------------
      #  robot_state_publisher 节点 ：订阅 joint_state，用于发布机器人 TF 与状态信息
      # -------------------------------------------------------------------------------
    
      【7) 函数内部的普通注释风格】
      - 简单、局部说明用单行注释：
        # 自定义包
        # 自定义路径
      - 需要解释“为什么这样组织”的地方，用 2~4 行短说明，不要长段落
    
      【8) 输出要求】
      - 输出完整、已注释好的 .py 文件
      - 若原文件已有部分注释：保持并补齐缺失分区，整体风格统一
    
    ~~~

  ## 以"//"为注释的文件

  ### hpp

  1. prompt

    ~~~prompt
    
      你是一个工程化 C++ 头文件维护者。请对我提供的 .hpp 文件补充统一风格的 // 注释，要求如下（必须严格遵守）：
    
      【总体原则】
      - 只补充注释，不改变任何代码逻辑、不改符号命名、不改缩进排版（除非为了对齐注释空格，但不要大改格式）
      - 注释语言为中文（允许夹少量英文关键字/术语，如 Action Server / MoveIt）
      - 注释重点解释：模块职责、接口意图、数据含义、分组结构
      - 不解释显而易见的 C++ 语法（如 include、namespace、class 语法本身）
      - 头源分离：头文件关注“接口与职责”，不要写实现细节
      - 要求简洁，简洁，简洁，重要的事情说三遍
    
      【2) include 分组（必须分组并加简短标题）】
      - 用普通单行注释作为分组标题，例如：
        // ROS2
        // MoveIt
        // Msg
        // C++
      - 每组之间保留一个空行
      - 若出现“不建议 include detail 头”的提示，保留为块注释或单行注释，内容可更工程化但不要冗长
    
      【3) 顶层 enum / struct / class 的大块注释（必须使用大标题块）】
      在每个重要 enum/struct/class 前，使用以下标题块之一：
    
      (1) 简单标题块（适合 enum / 简单模块）（上下都是空行）
      // ============================================================================
      //  <标题>
      // ============================================================================
    
      (2) 带说明的标题块（适合 struct/class/复杂概念）（上下都是空行）
      // ============================================================================
      //  <标题>
      // ----------------------------------------------------------------------------
      //  - <职责/用途1>
      //  - <输入/输出或关键字段含义>
      //  - <控制/状态/约束说明>
      // ============================================================================
    
      要求：
      - 标题要能概括作用（例如 Plan option / GoalContext / Action Server）
      - bullet 2~5 条，解释“这个类型是干什么的”
      - enum 的每个枚举值：在同一行末尾用 // 注释（简短说明用途/策略）
        例如：
        NORMAL = 0, // IK + planning
      - struct 的关键字段：必要时在行尾 // 注释含义（尤其是 atomic、error_code、topic 名、单位/范围等）
    
      【4) 类内部成员注释规则】
      - 成员变量：用“普通注释”分割区域，并在每个区域上方写标题，例如：
        // Parameters
        // ROS interfaces
        // Runtime state
        // 当前活跃 goal（用于 cancel / preempt）
      - 只有“语义不明显/容易误解”的成员才加行尾注释；明显的不要硬注释
    
      【5) 函数分组注释（必须使用短分隔块）】
      在类内部，用如下格式对方法进行功能分组（固定结构）：（上下都是空行）
    
        // -----------------------------------------------------------------------
        //  <分组标题>
        // -----------------------------------------------------------------------
    
      示例分组标题风格（按实际代码选择）：
      - Init / utils
      - Planning
      - Action callbacks
      - Worker
      - Helper
    
      规则：
      - 分组块之间保留一个空行
      - 对每个函数是否写行尾注释：仅当函数名不足以表达用途时才写一句短注释（不要写长段落）
    
      【6) namespace 注释】
      - namespace 开头无需解释
      - namespace 结束必须保留形如：} // namespace <name>
    
      【7) 输出要求】
      - 输出“完整的已注释头文件”，而不是建议列表
      - 如果原文件已存在部分注释：保持风格一致并补齐缺失部分，不重复啰嗦
    
    ~~~
  2. 示例

    ~~~hpp
    
      #pragma once
    
      // ============================================================================
      //  ArmSolveServer
      // ----------------------------------------------------------------------------
      //  - ROS2 Action Server（Move.action）
      //  - 使用 MoveIt 进行轨迹规划
      //  - 将规划轨迹拆点发布为 /joint_commands
      //  - 支持 cancel / preempt（新 goal 抢占旧 goal）
      // ============================================================================
    
      // ROS2
      #include <memory>
      #include <rclcpp_action/rclcpp_action.hpp>
      #include <rclcpp_components/register_node_macro.hpp>
    
      // MoveIt
      #include <moveit/move_group_interface/move_group_interface.h>
    
      // Msg
      #include "engineer_interfaces/action/move.hpp"
      #include "engineer_interfaces/msg/joint.hpp"
      #include "engineer_interfaces/msg/joints.hpp"
      #include <geometry_msgs/msg/pose_stamped.hpp>
      #include <moveit_msgs/msg/robot_trajectory.hpp>
    
      // C++
      #include <algorithm>
      #include <atomic>
      #include <cstdint>
      #include <mutex>
      #include <array>
      #include <string>
      #include <thread>
      #include <vector>
    
      /*
      不建议直接 include detail 头（如 moveit_msgs/msg/detail/...）
      */
    
      namespace arm_solve {
    
      // ============================================================================
      //  Plan option
      // ============================================================================
    
      enum class PlanOptionType {
        NORMAL = 0, // IK + planning
        CARTESIAN = 1,
        JOINTS = 2
      };
    
      // ============================================================================
      //  GoalContext（每个 goal 独立）
      // ----------------------------------------------------------------------------
      //  - 输入：option + target_pose
      //  - 控制：cancel_requested（cancel / preempt）
      //  - 输出：traj_msg（规划结果）
      // ============================================================================
    
      struct GoalContext {
        PlanOptionType option;
        geometry_msgs::msg::PoseStamped target_pose;
        std::array<float, 6> target_joints{{0.f, 0.f, 0.f, 0.f, 0.f, 0.f}};
        std::atomic<bool> cancel_requested{false};
        std::atomic<uint8_t> error_code{0};
        std::string error_msg;
        moveit_msgs::msg::RobotTrajectory traj_msg;
      };
    
      // ============================================================================
      //  Action Server
      // ============================================================================
    
      using Move = engineer_interfaces::action::Move;
      using GoalHandleMove = rclcpp_action::ServerGoalHandle<Move>;
    
      class ArmSolveServer : public rclcpp::Node {
      public:
        explicit ArmSolveServer(
            const rclcpp::NodeOptions &options = rclcpp::NodeOptions());
    
      private:
    
        // Parameters
        std::string group_name_;
        double goal_pos_tolerance_;
        double goal_ori_tolerance_;
        double planning_time_;
        int num_planning_attempts_;
        rclcpp::Time last_plan_time_;
    
        // ROS interfaces
        rclcpp::TimerBase::SharedPtr init_timer_;
        rclcpp::Subscription<engineer_interfaces::msg::Joints>::SharedPtr
            joint_state_verbose_sub_;
        rclcpp::Publisher<engineer_interfaces::msg::Joints>::SharedPtr joint_cmd_pub_;
        std::unique_ptr<moveit::planning_interface::MoveGroupInterface> move_group_;
        rclcpp_action::Server<Move>::SharedPtr action_server_;
    
        // Runtime state
        engineer_interfaces::msg::Joints current_joints_;
        std::mutex current_joints_mutex_;
    
        // 当前活跃 goal（用于 cancel / preempt）
        std::mutex active_mtx_;
        std::weak_ptr<GoalHandleMove> active_goal_handle_;
        std::shared_ptr<GoalContext> active_ctx_;
    
        // -----------------------------------------------------------------------
        //  Init / utils
        // -----------------------------------------------------------------------
        void lateInit();
        void initParameters();
        void logParameters() const;
        bool isMoveGroupReady() const;
    
        // -----------------------------------------------------------------------
        //  Planning
        // -----------------------------------------------------------------------
        bool planTrajectory(const std::shared_ptr<GoalContext> &ctx,
                            moveit_msgs::msg::RobotTrajectory &out_traj_msg);
    
        bool planTrajectoryByNormal(const std::shared_ptr<GoalContext> &ctx,
                                    moveit_msgs::msg::RobotTrajectory &out_traj_msg);
    
        bool planTrajectoryByCartesian(const std::shared_ptr<GoalContext> &ctx,
                                  moveit_msgs::msg::RobotTrajectory &out_traj_msg);
    
        bool planTrajectoryByJoints(const std::shared_ptr<GoalContext> &ctx,
                                  moveit_msgs::msg::RobotTrajectory &out_traj_msg);
    
        void jointCallBack(const engineer_interfaces::msg::Joints::SharedPtr msg);
    
        // -----------------------------------------------------------------------
        //  Action callbacks
        // -----------------------------------------------------------------------
        rclcpp_action::GoalResponse
        handle_goal(const rclcpp_action::GoalUUID &uuid,
                    std::shared_ptr<const Move::Goal> goal);
    
        rclcpp_action::CancelResponse
        handle_cancel(const std::shared_ptr<GoalHandleMove> gh);
    
        void handle_accepted(const std::shared_ptr<GoalHandleMove> gh);
    
        // -----------------------------------------------------------------------
        //  Worker
        // -----------------------------------------------------------------------
        void execute(const std::shared_ptr<GoalHandleMove> gh,
                    const std::shared_ptr<GoalContext> &ctx);
    
        void publishTrajectoryPoints(const std::shared_ptr<GoalHandleMove> gh,
                                    const std::shared_ptr<GoalContext> &ctx);
    
        // -----------------------------------------------------------------------
        //  Helper
        // -----------------------------------------------------------------------
        inline bool isCanceled(const std::shared_ptr<GoalHandleMove> &gh,
                              const std::shared_ptr<GoalContext> &ctx) const {
          return (gh && gh->is_canceling()) || (ctx && ctx->cancel_requested.load());
        }
      };
    
      } // namespace arm_solve
    
    ~~~

  ### cpp

  1. 规则：

    - include 分组 与 hpp 一致（普通 // 注释）
    - 必须有 ctor 大标题块
    - 函数分组名与 hpp 对应
    - 但在 cpp 中：函数分组统一升级为 = 分隔的大标题块
    - cpp 关注 实现逻辑与执行流程，不重复接口语义

  2. Prompt

    ~~~ prompt
    
      你是一个工程化 C++ 源文件维护者。请对我提供的 .cpp 文件补充统一风格的 // 注释，要求如下（必须严格遵守）：
    
      【总体原则】
      - 只补充注释，不改变任何代码逻辑、函数签名、命名或执行顺序
      - 注释语言为中文（允许必要的英文工程术语）
      - cpp 文件关注“实现逻辑、执行流程、运行时行为”
      - 不重复 hpp 中已经清晰表达的接口含义
      - 不解释显而易见的 C++ 语法
      - 要求简洁，简洁，简洁，重要的事情说三遍
    
      【1) include 分组规则（与 hpp 完全一致）】
      - 使用普通单行注释作为分组标题，例如：
        // Eigen / STL
        // MoveIt
        // ROS
      - 每个分组之间保留一个空行
      - include 顺序和内容不做任何调整
    
      【2) 构造函数分区（必须存在）】
      - 当 cpp 中包含类的构造函数实现时，必须在构造函数前添加如下大标题块：（上下都是空行）
    
      // ============================================================================
      //  ctor
      // ============================================================================
    
      规则：
      - 仅用于构造函数实现
      - 如果有多个构造函数，统一放在该分区内
      - 不在此块中写业务逻辑说明，只说明“构造阶段做了什么”（如参数声明、接口初始化、延迟初始化策略等）
    
      【3) 函数实现分组规则（核心要求）】
      - cpp 中的函数实现必须按功能分组
      - 分组名称应与 hpp 中的函数分组保持一致
      - 但分隔样式必须“升级”为 `=` 分隔的大标题块
    
      统一格式如下（固定）：（上下都是空行）
      // ============================================================================
      //  <分组标题>
      // ============================================================================
    
      示例分组标题（按实际代码选择）：
      - Init / utils
      - Planning
      - Action callbacks
      - Worker
      - Helper
    
      【重要区别说明】
      - hpp 中使用的是：（上下都是空行）
        // -----------------------------------------------------------------------
      - cpp 中对应分组必须使用：
        // ============================================================================
    
      【4) 单个函数实现的注释规则】
      - 函数体内部：
        - 用普通 // 注释解释“这一段代码在做什么”
        - 重点说明：状态变化、条件判断意图、异常/失败路径
      - 不逐行翻译代码
      - 复杂 if / loop / early return 前，必须有简短说明
    
      【5) 与 hpp 的关系约束】
      - 不重复 hpp 中已经说明的“函数用途”
      - cpp 中可以补充：
        - 为什么这样实现
        - 执行顺序的原因
        - 与外部组件（MoveIt / ROS2 / 线程 / action）的交互细节
    
      【6) namespace 注释】
      - namespace 结束必须保留形如：
        } // namespace <name>
    
      【7) 输出要求】
      - 输出完整、已注释好的 .cpp 文件
      - 若原文件已有部分注释：
        - 保留原注释
        - 补齐缺失的分区与实现说明
        - 风格必须统一
    ~~~
